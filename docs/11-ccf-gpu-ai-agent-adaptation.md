# CCF 国产开源 GPU AI 创新生态赛任务三适配说明

本文面向 CCF 开源大赛“国产开源 GPU AI 创新生态赛”任务三：基于国产算力平台的 AIGC 与智能体开发与应用。目标是在现有“孔明职配”项目基础上，补齐参赛材料口径、明确已实现能力，并列出接入 Gitee.AI / 沐曦资源包 API 前需要确认和修改的事项。

## 1. 项目定位

孔明职配是一款面向学生求职场景的 AIGC 与多智能体应用。系统围绕“简历理解、岗位匹配、求职建议、模拟面试、自由问答”构建连续工作流，帮助学生从个人经历出发理解适配岗位，并获得可执行的简历优化和面试准备建议。

目标用户：

- 高校本科生、研究生、应届毕业生。
- 准备实习、校招、转专业求职的学生。
- 可辅助高校就业指导老师、训练营导师进行简历诊断和面试辅导。

核心场景：

- 学生上传 PDF、图片或文本简历，系统解析为结构化画像。
- 系统结合简历信息生成岗位方向、岗位匹配度和推荐理由。
- 学生输入意向岗位 JD 后，系统分析岗位要求与简历差距。
- AI 助手支持多轮求职咨询。
- AI 模拟面试支持综合面、技术面、HR 面三类模式。

## 5. Gitee.AI / 沐曦 API 与模型选择建议

### 5.1 接口选择

Gitee.AI 模力方舟提供 OpenAI 风格接口，文本生成接口示例为：

```text
https://ai.gitee.com/v1/chat/completions
```

这与当前项目的后端代理结构兼容。因此推荐保留现有前端调用方式，把 `server/arkCore.js` 从 Ark 专用代理改造为通用 OpenAI 兼容 Provider。

建议环境变量：

```text
MODEL_PROVIDER=gitee-ai
MODEL_BASE_URL=https://ai.gitee.com/v1
MODEL_API_KEY=由部署平台安全注入
MODEL_TEXT_NAME=参赛账号可用的文本模型 ID
MODEL_VISION_NAME=参赛账号可用的视觉模型 ID
```

保留兼容变量：

```text
ARK_API_KEY
ARK_BASE_URL
```

这样不会破坏当前已能运行的 Demo，也可以在提交赛题版本时切换到 Gitee.AI。

### 5.2 模型选择

本项目既需要文本推理，也需要图片简历识别。模型选择优先级如下：

首选方案：一个视觉语言模型覆盖全部任务。

- 如果 Gitee.AI 沐曦资源包中提供 Qwen2.5-VL、Qwen2-VL、InternVL、GLM-4V 等视觉语言模型，优先选择其中上下文长度较长、推理质量较稳定的模型。
- 优点：同一个模型可覆盖图片简历识别、文本简历结构化、岗位匹配、AI 助手和模拟面试，满足“至少 1 个大模型接入”的要求。
- 风险：复杂文本推理质量和响应速度可能不如专用文本大模型。

增强方案：视觉模型 + 文本模型双模型。

- 视觉模型用于 `resume-vision`：图片简历、PDF 页面截图、视觉 OCR。
- 文本模型用于 `resume-structure`、`job-recommendations`、`jd-analysis`、`match-analysis`、`career-chat`、`interview-feedback`。
- 优点：质量和速度更容易平衡。
- 风险：需要更多 API 配额和更完整的调用日志。

现阶段不建议直接在代码中写死具体模型 ID。原因是赛题强调 Gitee.AI 平台提供的沐曦资源包 API，而具体可用模型取决于参赛账号资源包。应先在控制台确认模型列表，再写入 Vercel 环境变量。

### 5.3 对 PDF 和图片解析的建议

当前项目已使用 PDF.js 文本层解析和视觉兜底。为了适配 CCF 赛题并提升复杂 PDF 的稳定性，推荐增加 Gitee.AI 文档解析/OCR 能力作为第三层兜底：

1. PDF.js 文本层质量足够时，直接结构化。
2. 文本层乱码、缺失或中文主体不足时，将 PDF 页面截图交给视觉模型。
3. 仍不稳定时，调用 Gitee.AI 文档解析或 OCR 接口，获得更完整文本后再交给文本模型。

这样既保留当前前端体验，又能体现国产算力平台在文档智能处理中的作用。
